# CODE IT! Build it. Break it. Fix it.

*A game by **Web Development Services**.*

A short-form game where young programmers take ridiculous website jobs from ridiculous
clients and complete them by writing real HTML, CSS and JavaScript.
Loop: **receive job → write code → RUN → see what broke → fix → ship → next job**.

## Play and test it with Python in VS Code (no Node needed)

You only need **Python 3.10+** and VS Code with the Python extension (VS Code offers to install it when you open the folder).
The game is already built into `web/`, and the server uses only the Python standard library, so there is nothing to `pip install`.

1. **File → Open Folder…** and pick this `code-it` folder.
2. **Run and Debug** (Ctrl+Shift+D) → choose **Play CODE IT! (Python server)** → press F5.
   The game opens at <http://localhost:8000>. Breakpoints in `server/*.py` work.
   (Or in a terminal: `python run.py --open`, and `py run.py --open` on Windows.)
3. **Testing** panel (the flask icon) → run the 15 server tests. Or **Terminal → Run Task… → Python: run server tests**,
   or `python -m unittest discover -s tests/python -t .`

Let coworkers on your network play: `python run.py --host 0.0.0.0` and share `http://<your-ip>:8000`.
Progress, achievements and learning analytics are saved in `server/data/codeit.sqlite3` (delete it to start fresh).
Settings can also come from environment variables, see `.env.example`.

### The Python server

```
run.py                 start the server (python run.py --help)
server/app.py          HTTP server: serves web/ and the JSON API below, security headers, rate limit
server/rules.py        checks every report the browser sends (the browser is never trusted)
server/db.py           SQLite storage: players, progress, achievements, analytics
server/levels.json     level data exported from src/levels (regenerated by npm run build)
tests/python/          unittest tests for the rules and the API
.vscode/               launch (F5), tasks, test discovery, recommended extensions
```

API: `GET /api/health`, `GET /api/game/config`, `GET /api/levels` (paging, `category`, `difficulty`, `full=1`),
`GET /api/levels/<id>`, `POST|GET /api/player`, `POST /api/progress`, `POST /api/achievements`,
`POST /api/analytics/events`, `GET /api/leaderboard`. Writes accept an `Idempotency-Key` header so retries are stored once.
The server refuses progress for levels skipped out of order and impossible scores, and never stores player code.

## Changing the game itself (needs Node 20+)

The game UI is TypeScript in `src/`. After changing it, rebuild `web/` so the Python server picks it up:

```bash
npm install
npm run dev        # hot-reload dev server at http://localhost:5173 (no Python API)
npm test           # unit tests (vitest)
npm run build      # typecheck + export server/levels.json + production build to web/
npm run serve      # python run.py
npm run e2e        # real-Chromium gameplay tests against the static build
npm run e2e:py     # the same tests through the Python server, incl. progress sync
```

These are also VS Code tasks. `npm run e2e` looks for Chromium at `/opt/pw-browsers/...`; set `CHROMIUM_PATH` to point it elsewhere.

## What's in the MVP

- **10 jobs**: HTML structure, CSS styling, Flexbox, JS events, a multi-file debug job,
  a profile card, a product card with state, a responsive layout, a JS logic debug job, and a final mini site.
- **Change requests**: three jobs have a mid-level twist ("THE BOSS WANTS IT IN BLUE.") that adds a requirement after you pass.
- **Editor**: CodeMirror 6 with HTML/CSS/JS tabs, syntax highlighting, line numbers, undo/redo,
  Format (Prettier, lazy-loaded), Reset (undoable), live lint squiggles, Ctrl/Cmd+Enter to run.
- **Live preview** in a sandboxed iframe, updated as you type. A console tab shows `console.log`, errors and `alert()`.
- **Deterministic validation**: every requirement is machine-readable data (`src/levels/data.ts`).
- **Feedback**: SUCCESS/FAILED, what failed + why + a nudge, what worked, clickable error lines, BYTE's reaction.
- **Progressive hints**: concept → direction → almost there → example. Hints only cost a bonus, never XP.
- **XP & stars**: completion, first try, no hints, debugging, experimenting (4+ runs), beat the deadline, accessibility, performance. Replays give half XP.
- **12 achievements**, including one for causing your first bug.
- **Audio**: all sounds go through `AudioManager.play(name)`, synthesized with Web Audio (original, no files).
  Master/effects/music volume, mute, optional music, and visual captions for every sound.
- **Accessibility**: keyboard play throughout, focus-trapped dialogs, ARIA tabs, screen-reader announcements
  of results, reduced motion (respects the OS setting), captions, light and dark themes.
- **Responsive**: 3 columns at ≥1200px, ticket drawer at 820 to 1199px, tabbed single panel with a pinned RUN button on phones.
- **Offline-first**: levels, validation, sounds and progress are all local. Nothing needs a server.

## How player code is kept away from the game

- Player code runs in `<iframe sandbox="allow-scripts">` without `allow-same-origin`, so it has an opaque origin
  and cannot read the game's DOM, storage or cookies. `alert()`/`confirm()` are replaced; links and forms can't navigate away.
- A CSP inside the iframe blocks all network requests except images and fonts.
- Results are only accepted from the exact frame the game created, with a per-run random token that the runtime
  keeps in a closure and removes from the DOM before player code runs. Forged `postMessage` results are ignored (tested).
- Loops get a time budget and every validation has a 2.5s timeout.
- The iframe document is built from `srcdoc`, which inherits the parent page's CSP. If you add a CSP header to the
  game, it must allow `'unsafe-inline'` scripts for srcdoc frames, or move the sandbox to a separate origin.
- Validation runs in the player's browser, so it is a learning check, not an anti-cheat.
  Anything competitive (leaderboards) must re-validate on the server (`POST /api/code/validate`).

## Adding a level

Add an object to `LEVELS` in `src/levels/data.ts`, add its reference solution to `tests/e2e/solutions.mjs`, then run
`npm run build && npm run e2e`. The e2e suite fails if the starter code passes or the solution doesn't.

Rule types: `element`, `text`, `attr`, `style` (computed style: `equals`, `oneOf`, `not`, `notIn`, `contains`,
`notContains`, `minPx`, `hue`), `sameRow`, `stacked`, `noOverflow`, `noRuntimeErrors`, `interact` (click/type steps
then expectations), `source` (regex on source, comments stripped), `htmlBalanced`. Any requirement can set
`viewport` (e.g. 375 for phone checks) or `bonus`.

## Other hosting

`web/` is a static site and also works on any static host with no server: progress then stays in the browser only.
To sync with a server on another origin, set `VITE_API_BASE_URL` (see `.env.example`) and rebuild.
The client (`src/api/client.ts`) sends writes through an idempotent, retrying offline queue.

## Measured locally (headless Chromium, local server)

- Title screen visible ~150 to 200ms. The editor chunk (≈196KB gzip) is lazy-loaded and prefetched while idle.
- Validation for a typical run: ~80 to 130ms including sandbox boot (the <100ms target is met for simple levels,
  not for every multi-frame level yet).
- An infinite loop is stopped and reported in ~1.4s.

These are local numbers, not production measurements.
